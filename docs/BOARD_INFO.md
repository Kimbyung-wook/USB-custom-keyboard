# 보드 정보와 GUI 자동 구성 설계안

> 문서 성격: **설계** (HELLO 보드 정보, 보드 목록, 칩 표). 현재 보드별 값은 [BOARDS.md](BOARDS.md), 사용 절차는 [MANUAL.md](MANUAL.md)

## 목표

- 키보드가 자기 정보를 GUI에 알림: **칩, 키 수, 노브 수, 키 배치, 저장 용량, 보드 이름**
- GUI는 그 정보로 **화면(키 그림, 편집 칸, 패턴 암호 버튼)을 만듦**. "키 6개 + 노브 1개"를 코드에 박아 두지 않음
- 펌웨어 업데이트 창은 칩에 맞는 **최대 크기와 업로드 도구**를 고르고, 고른 펌웨어 파일이 **이 보드용인지** 확인함
- 지금 키보드(6키 + 노브 1개, CH552)와 이미 배포된 펌웨어(1.0~1.2.1)는 그대로 동작해야 함
- 핵심: 칩 이름보다 **키/노브 수를 키보드가 직접 알려 주는 것**
  - 같은 칩이라도 키 수·배치가 다름 (예: CH32V203의 8키·9키)
  - 칩이 달라도 배치가 같을 수 있음

## 1. 슬롯 번호 규칙 (일반화)

- 지금 규칙(키 0~5, 노브 6~8, 패턴 암호 9)을 그대로 늘린 형태
- 6키 + 노브 1개에서는 지금과 **완전히 같은 번호**

| 슬롯 | 입력 |
|---|---|
| `0` ~ `K-1` | 키 K개 (배치 순서: 윗줄 왼쪽부터, 행 우선) |
| `K + 3n + 0` | 노브 n 시계 방향 |
| `K + 3n + 1` | 노브 n 반시계 방향 |
| `K + 3n + 2` | 노브 n 누르기 |
| `S` (= `K + 3N`) | 패턴 암호 (블롭에만 있음, 타이핑하지 않음) |
| `S + 1` | 설정 슬롯 (자동 잠금 시간, 펌웨어 1.4, [PROTOCOL.md](PROTOCOL.md)) |

- 슬롯 수 `S = K + 3N` = HELLO 바이트 6(지금도 있는 "슬롯 수")
- 블롭 형식은 그대로. 블롭의 슬롯 수는 `S`(패턴 없음), `S + 1`(패턴 있음), `S + 2`(설정 슬롯까지)
- 패턴 암호의 각 단계는 `0` ~ `S-1` 사이의 슬롯 번호(지금은 0~8)
- 한계: `S ≤ 63` (펌웨어 `config.h`에서 `#error`로 검사)
  - 블롭 형식으로는 255까지 가능
  - 슬롯마다 2바이트 길이 정보가 붙어, 작은 DataFlash(128바이트)에서는 슬롯이 많을수록 문자열 자리가 줄어듦 (CH32V203 보드는 4096바이트)
  - GUI 화면이 감당할 수 있는 정도로 제한
  - 예: 키 15개 + 노브 3개 = 24

## 2. HELLO 확장

- HELLO 응답(64바이트)의 바이트 17부터 보드 정보를 붙임. 펌웨어 1.3부터 채움

| 바이트 | 내용 | 6키 키보드 값 |
|---|---|---|
| 17 | 보드 정보 버전 (`0` = 없음, `1` = 이 표) | `1` |
| 18 | 칩 ID: 부트로더 Detect가 돌려주는 값과 같은 번호 | `0x52` (CH552) |
| 19 | 키 수 K | `6` |
| 20 | 노브 수 N | `1` |
| 21 | 키 배치 행 수 R (열 수는 `ceil(K / R)`, 마지막 줄은 덜 찰 수 있음) | `2` |
| 22 | 기능 비트: bit0 RGB LED 있음, bit1 패턴 암호 지원, bit2 무선(예약), bit3 설정 슬롯(펌웨어 1.4) | `0x03` (1.4부터 `0x0B`) |
| 23 | 예약 (`0`) | `0` |
| 24~31 | 보드 이름 (ASCII 8바이트, 남는 곳은 `0`) | `"MK6K1N"` |
| 32~35 | 칩 고유 ID (4바이트, 모르면 `0`) — 아래 "정할 것" 3번 | `7D E2 0F BD` |

- 바이트 7~8 **저장 용량**(지금도 있음)은 그대로 씀. 칩마다 DataFlash가 다르면 펌웨어가 그 값을 보냄
- 바이트 17이 `0`이면(펌웨어 1.0~1.2.x, 그 자리가 0) GUI는 **기본 보드**로 봄: CH552, 키 6개, 노브 1개, 2행, 이름 `MK6K1N`
- 펌웨어 쪽 비용 예상: 상수 19바이트를 `__code` 표에서 복사하는 반복문 정도, 약 40~60바이트(실제 결과는 6절)

### 프로토콜 버전을 올릴지

| 방법 | 장점 | 단점 |
|---|---|---|
| **A. v2 그대로, 바이트 17로 구분 (권장)** | 예전 GUI(1.2)도 새 펌웨어의 6키 키보드와 그대로 동작. 예전 GUI는 슬롯 수가 9가 아닌 보드를 "슬롯 수가 맞지 않습니다"로 거부하므로 잘못 쓰지도 않음 | 버전 번호만 보고는 보드 정보 유무를 모름(바이트 17을 봐야 함) |
| B. v3로 올림 | 규칙이 깔끔함 | 예전 GUI가 6키 키보드까지 "지원하지 않는 버전"으로 거부함 |

## 3. GUI 구조

### 3-1. `Board` (새 개념, `gui/core/protocol.py`)

```python
@dataclass(frozen=True)
class Board:
    chip_id: int          # 0x52
    keys: int             # K
    knobs: int            # N
    rows: int             # R
    name: str             # "MK6K1N"
    capacity: int         # HELLO 바이트 7~8
    uid: bytes = b""

    slot_count  -> K + 3N
    lock_slot   -> slot_count
    slot_names()        # ["A".."F", "1↻", "1↺", "1●", ...]  (노브가 하나면 지금처럼 "CW/CCW/PRESS")
    slot_labels_ko()    # ["키 A", ..., "노브 시계 방향", ...] (노브가 여럿이면 "노브 2 시계 방향")
    lock_step_names()   # 패턴 암호 버튼 글자
    chip -> ChipInfo    # 아래 칩 표에서 찾음
```

- 키 이름: 26개까지 `A`~`Z`, 그 이상은 `K27`처럼 번호. 지금 키보드는 A~F 그대로
- `DEFAULT_BOARD`: 위의 기본 보드. 바이트 17이 `0`이면 사용

### 3-2. 고정값을 없앨 곳

| 파일 | 지금 | 바꿀 것 |
|---|---|---|
| `protocol.py` | `SLOT_COUNT = 9`, `SLOT_LOCK = 9`, `SLOT_NAMES`, `SLOT_LABELS_KO`, `LOCK_STEP_NAMES`, `SLOT_KNOB_*` | `Board`의 속성으로. `encode_blob`/`decode_blob`/`blob_size`/`lock_error`가 `slot_count`를 인자로 받음 |
| `protocol.py` `HelloInfo` | 바이트 0~16만 해석 | 바이트 17~35 해석, `board` 속성 |
| `device.py:117` | 슬롯 수가 9가 아니면 연결 거부 | `slot_count == K + 3N`인지만 확인(보드 정보와 슬롯 수가 어긋나면 거부) |
| `widgets.py` `DeviceView` | 키 6개 2×3 + 노브 1개 고정 | `Board`로 만듦: 키 R행 격자 + 노브 N개를 오른쪽에 세로로. 연결할 때마다 다시 만듦 |
| `widgets.py` `LockPatternEditor` | 버튼 9개 고정 | `slot_count`개 버튼(키 격자 + 노브별 3개) |
| `app.py` | `[""] * p.SLOT_COUNT` 여러 곳 | `self.board.slot_count`. 연결이 끊기면 지금처럼 화면을 비우고, 연결되면 그 보드로 화면을 다시 만듦 |
| `backup.py` (JSON) | 슬롯 9개 고정 | 파일에 `board`(이름, 키/노브 수) 기록. 불러올 때 보드가 다르면 묻기: 같은 이름의 슬롯(예: "키 A")끼리만 옮길지, 취소할지 |
| `transport.py` `MockDevice` | 6키 고정 | `board` 인자로 아무 배치나 흉내(테스트용) |

### 3-3. 화면 배치 규칙

- 키: `R`행, 열 수 `ceil(K / R)`. 버튼 최소 크기는 키 수에 따라 줄임(예: 12개 이상이면 72×56)
- 노브: 키 격자 오른쪽에 노브마다 원 하나 + 동작 버튼 3개. 노브 0개면 노브 영역 숨김
- 창 제목/연결 막대: `● 연결됨 · MK6K1N (CH552, 키 6 + 노브 1) · 펌웨어 v1.3.0 (빌드 …) · 용량 128바이트`
- 키가 많아도 편집 칸(오른쪽 매크로 편집기)은 하나 → 화면 크기는 크게 안 늘어남

## 4. 칩 표와 펌웨어 업데이트

- `gui/core/chips.py`(새 파일) 한 곳에 칩별 값을 모음
- 업데이트 창의 `CH552`, `14336` 고정값을 이 표로 바꿈

<!-- gen:chips -->
| 칩 ID | 칩 | 펌웨어 영역 | 지원 | 비고 |
|---|---|---|---|---|
| 0x51 | CH551 | 10,240 B | 아니오 | 펌웨어 미지원 (USB 버퍼를 줄여야 함) |
| 0x52 | CH552 | 14,336 B | 예 | - |
| 0x54 | CH554 | 14,336 B | 아니오 | 확인하지 않은 칩 |
| 0x19 | CH32V203 | 52,992 B | 아니오 | vnproch55x로는 올리지 못합니다. 자체 부트로더(hidboot)로 올립니다 (docs/BOOTLOADER_CH32V203.md) |
<!-- /gen:chips -->

- 표는 `tools/gen_docs.py`가 `gui/core/chips.py`에서 만듦. "지원"은 vnproch55x로 올릴 수 있는지
- 업로드 도구: CH551·CH552·CH554는 vnproch55x `-t <칩>`(CH554는 확인 필요). CH32V203은 자체 HID 부트로더(`hidboot.py`, `.bin`), 처음 한 번만 wchisp + BOOT 브리지 ([BOOTLOADER_CH32V203.md](BOOTLOADER_CH32V203.md))
- CH32V203은 SAYO_3X3, SAYO_2X4에서 지원(자체 부트로더)

- **업데이트 모드 칩 목록**: 부트로더 Detect가 돌려준 칩 ID로 이 표를 찾아 최대 크기와 업로드 도구를 정함
  - 표에 없거나 "미지원"이면 [장입]을 막고 이유를 보여 줌
- CH32V203 칩 ID: wchisp `CH32V203C8U6[0x3019]` = 칩 0x30, 계열 0x19. HELLO와 GUI의 칩 ID는 계열 값 `0x19` (확인됨)
- **펌웨어 파일 확인**: 펌웨어 안에 식별 문자열을 하나 넣음(예: `"MKFW1:MK6K1N:CH552"`, 약 20바이트). GUI가 hex에서 찾아 확인:

| 경우 | 동작 |
|---|---|
| 칩이 업데이트 모드의 칩과 다름 | 장입 막음 |
| 보드 이름이 연결되어 있던 키보드와 다름 | "다른 키보드용 펌웨어입니다" 경고, 사용자 확인 후 장입 |
| 문자열 없음(예전 펌웨어, 다른 사람의 펌웨어) | "확인할 수 없는 펌웨어" 경고 |
| CH32V203: 보드가 부트로더 HELLO 보드와 다르거나 문자열 없음 | 빨간 경고, "강제 장입" 확인(기본 취소). `hidboot`은 지우기 전에 거부, `--force`로만 |

- 연결된 키보드의 칩 고유 ID(HELLO 32~35) = 업데이트 모드 칩 목록의 ID이면 "방금 연결되어 있던 키보드"로 표시
  - 여러 대를 꽂아 두었을 때 헷갈리지 않게 함

## 5. 보드 구분

- 칩은 두 계열(CH552, CH32V203)이지만 **같은 칩에 키 수가 다른 키보드**도 있고, 같은 키 수라도 기판이 다를 수 있음
- 그래서 칩이나 키 수가 아니라 **보드(제품·기판)** 기준으로 구분함
- 보드마다 이름 하나, 펌웨어 빌드 하나. 칩, 키/노브 수, 핀 배치, 부트로더 진입 핀은 보드에 딸린 값
- 키 수를 실행 중에 알아내지 않음: 연결되지 않은 핀은 "안 눌린 키"와 똑같이 읽혀 구분 불가
- 보드 이름(HELLO 24~31, 8자) 규칙:
  - 기본: `MK` + 키 수 + `K` + 노브 수 + `N` (예: `MK6K1N`)
  - 키 수가 같은데 기판이 다르면 끝에 구분 글자 (예: `MK6K1NL`)
  - Sayo 제품은 `SAYO_<행>X<열>` (`SAYO_3X3`, `SAYO_2X4`). 펌웨어 1.7.0까지는 기판 표기(`3X3V_RGB`, `2X4V_RGB`)를 썼고, 지금은 `gui/core/boards.py` 별칭
  - CH32V203 보드 이름은 **정확히 8자** (USB 시리얼 문자열 길이, `usbd_desc.c`)
  - 8자 검사는 gcc 빌드(host 테스트, CH32V203)에서만. SDCC(CH552)는 코드 크기 때문에 끔

### 5-1. 보드 목록 (`gui/core/boards.py`, 새 파일)

- GUI가 아는 보드를 한 곳에 모음
- 펌웨어 보드 파일(`src/boards/*.h`)과 이름이 1:1로 맞음

| 항목 | 예 (지금 키보드) | 쓰는 곳 |

| 설명 | "6키 + 노브 1개 (CH552G)" | 처음 설치 때 목록 |
| 칩 계열 / 칩 ID | CH55x / `0x52` | 업데이트 모드 칩과 맞춰 보기, 업로드 도구 고르기 |

- 진입: CH552 보드는 ROM 부트로더 진입 핀 P1.5(키 D). CH32V203 보드는 자체 부트로더(진입 키), 처음 설치는 BOOT 브리지

- 핀 배치 그림·표: 보드 문서 2·3절 ([BOARDS.md](BOARDS.md))

- MK6K1NL: 이름 규칙(위 5절)대로 키 수가 같고 기판이 다른 보드 → 끝에 구분 글자 `L`(키마다 LED)
  - 공장 펌웨어(`1189:8890`)에서는 키로 업데이트 모드에 안 들어감 → 처음에는 D+ 풀업으로 올림([test_mk6k1nl](../tests/hw/mk6k1nl/test_mk6k1nl/README.md))
- 목록에 없는 보드도 HELLO에 보드 정보가 있으면 화면은 그대로 만들어짐(업데이트 창만 "알 수 없는 보드"로 조심스럽게 동작)

### 5-2. GUI가 보드를 알아내는 세 가지 상황

| 상황 | GUI가 알 수 있는 것 | 보드를 정하는 방법 |
|---|---|---|
| ① 우리 펌웨어가 돌고 있을 때 | HELLO로 보드 이름, 칩, 키/노브 수 전부 | **자동** (진행 순서 1번에서 만든 GUI `Board`) |
| ② 업데이트 모드 | 부트로더가 알려 주는 칩 종류와 칩 고유 ID뿐 | 직전에 연결되어 있던 키보드의 칩 고유 ID(HELLO 32~35)와 같으면 그 보드. 아니면 ③처럼 고르기 |
| ③ 처음 설치 (공장 펌웨어) | 칩 계열 정도 | **사용자가 보드 목록에서 고름**. 감지된 칩 계열에 맞는 보드만 보여 줌 |

③ 처음 설치 흐름:

1. [펌웨어 업데이트] 창을 열고 키보드를 업데이트 모드로 꽂음
   - 공장 펌웨어에는 BOOT 명령이 없음 → 보드 목록의 "사용자 안내"대로 들어감
2. 칩 목록에 칩이 나타나면 그 칩 계열의 보드만 보여 줌
   - 예: CH552 → `MK6K1N`, `MK6K1NL` / CH32V203 → `SAYO_3X3`, `SAYO_2X4`
3. 사용자가 보드를 고르면 그 보드의 펌웨어 파일을 기본으로 채우고 키 배치 미리 보기를 보여 줌(키 수를 눈으로 맞춰 보도록)
4. [장입] 후 키보드가 다시 시작하면 ①로 넘어가 HELLO로 확인. HELLO 보드 이름이 고른 보드와 다르면 알려 줌

- ③을 자동으로 정하지 않고 묻는 이유: 시중 매크로 키보드는 키 수가 달라도 공장 펌웨어의 USB ID(예: `1189:8890`)가 같을 수 있어, 공장 펌웨어 상태로는 몇 키인지 알 수 없음

### 5-3. 보드별 부트로더 진입 핀

- CH55x 부트로더는 업로드할 때 함께 쓰는 **진입 설정**(vnproch55x `-c`)에 따라 "어느 핀을 누른 채 꽂으면 업데이트 모드로 들어갈지"가 정해짐
- 진입 설정은 보드 목록의 `boot_config`에서 가져옴(MK6K1N: `BOOT_P15`, P1.5 = 키 D)
  - 업데이트 창은 **장입할 보드**를 목록에서 고르게 함(처음에는 HELLO의 보드)
  - 키보드를 식별할 수 없으면(공장 펌웨어, 보드 정보 없음, 목록에 없는 보드) 고른 보드가 맞는지 확인받은 뒤 장입(GUI 1.6.0)
- **진입 설정을 보드 목록에서 가져오는 이유**: 다른 기판에서 P1.5가 키가 아니면, 이 값으로 올린 뒤 다음 업데이트 때 업데이트 모드로 들어가기 어려워짐([TROUBLESHOOTING.md 2-3](TROUBLESHOOTING.md#2-3-다운로드-실패-후-장치가-전혀-인식되지-않음-복구))
- 고를 수 있는 진입 설정:

| 설정 | 방법 | 쓰는 경우 |
|---|---|---|
| **P1.5 풀다운** (`-c 1`) | P1.5에 연결된 키를 누른 채 꽂음 | 기본. 그 보드에서 P1.5가 어느 키인지 보드 목록에 적고, 안내 문구도 그 키 이름으로 만듦(예: "키 D를 누른 채") |
| **P3.6(USB D+) 풀업** (`-c 3`, CH55xDuino 기본값) | 키가 아니라 D+ 선을 3.3V에 이음 → 사용자가 하기 어려움 | P1.5에 키가 없는 보드에서만, 그 보드의 진입 방법(버튼, 패드 등)을 확인한 뒤 |

- 보드를 모를 때(목록에 없음): 장입을 막거나, 진입 설정을 바꾸지 않는 방법이 있는지 확인한 뒤 그 방법을 씀(아래 "확인할 것")
- BOOT 명령은 펌웨어가 직접 부트로더로 넘어가므로 진입 핀과 무관
  - 단, 펌웨어가 망가졌을 때의 복구 수단은 진입 핀뿐 → 이 값이 중요
- CH32V203 보드는 진입 설정 없음: 자체 부트로더가 진입 키(9키 키 7, 8키 키 5)를 직접 확인 ([BOOTLOADER_CH32V203.md](BOOTLOADER_CH32V203.md))

### 확인할 것

- vnproch55x에서 진입 설정을 바꾸지 않고 펌웨어만 쓰는 방법이 있는지(`-c` 생략 시 동작)

## 6. 펌웨어 쪽

- 보드별 값은 `src/config.h`가 아니라 **보드 파일** `src/boards/*.h`에 둠
  - 빌드할 때 `-DBOARD_MK6K1N`처럼 하나를 고름(`tools/build_fw.ps1 -Board mk6k1n`). 안 고르면 `mk6k1n`
  - 같은 기판을 쓰는 보드는 공통 기판 파일을 include함: `ch552_6k1n.h`(MK6K1N, MK6K1NL 공통)

| 파일 | 내용 |
|---|---|
| `src/boards/ch552_6k1n.h` | HAL 선택(`BOARD_HAL_CH55X`), 칩(`BOARD_CHIP`, `BOARD_CHIP_ID`), 키/노브/행 수(`BOARD_KEYS`, `BOARD_KNOBS`, `BOARD_ROWS`), 기능 비트, 핀 배치(`PIN_*`), 키 스캔 표(`BOARD_SWITCH_BITS`, P1에 있는 스위치 수 `BOARD_P1_SWITCHES`), 핀 배치 검사(`#error`) |
| `src/boards/mk6k1n.h`, `mk6k1nl.h` | 보드 이름(`BOARD_NAME`), LED 수(`BOARD_LED_COUNT`), 키별 LED 여부(`BOARD_KEY_LEDS`) |

- `SLOT_COUNT`는 `BOARD_KEYS + 3 * BOARD_KNOBS`로 계산(`src/config.h`)
  - 잠금 검사(`< SLOT_COUNT`)와 블롭 검사는 이 값을 씀
- 키 i는 슬롯 i를 입력함
- 노브가 여러 개인 보드는 이번 범위 밖(엔코더 읽기를 노브마다 반복해야 함). `config.h`가 `BOARD_KNOBS != 1`이면 `#error`. 보드 정보 형식만 미리 열어 둠
- HELLO 응답과 식별 문자열 추가로 117바이트 늘어남(8,151 → 8,268바이트, 1.3.0)
