# KEY12-JUZHEN_V01 (12키 + 노브 2)

- 요약 표: [BOARDS.md](../BOARDS.md#준비-중-보드). 같은 무선 보드: [SAYO_2B3](BOARD_SAYO_2X3B_RGB.md). 새 보드 절차: [NEW_BOARD.md](../NEW_BOARD.md#9-식별-전-보드)
- **상태: 칩 AC6321A 확정, 이식 준비 중(공장 펌웨어·부트로더 지워도 됨, 사용자 결정)**. 칩은 JieLi **AC6321A**(BD19 = AC632N 계열, BLE 전용, QFN32 4×4). 근거: UBOOT 이름 "BD19 UBOOT1.00", 실크 점 = 1번 핀, RF 8·OSC 9/10·USB0 14/15 배치, 23번 PB8 비접지(사용자 확인). 앞의 AC6956C 판단은 철회. UBOOT 진입은 PC USB만으로 됨(`03 EF EF`, 확인). 이식 가능성은 판단 보류([JieLi SDK·장입](#jieli-sdk장입-조사))

## 1. 개요

- 보드 ID: **JUZH_3B4** (8자, 3행 × 4열 + B = 블루투스, SAYO_2B3과 같은 방식). 노브 2개는 이름에 없음
- 기판 표기: `KEY12-JUZHEN_V01` (문서 파일 이름도 이 표기 그대로)
- 제품: 판매처 확인 필요(Sayo 기판 표기 형식과 달라 Sayo 제품이 아닐 가능성이 큼, 추정)
- 구성(사용자 관찰, 2026-11-15)
  - **12키 + 노브 2**, 3행 × 4열
  - 키마다 LED(종류 확인 필요)
  - 배터리, 전원 On/Off 스위치, 블루투스
  - 버튼 1개: 누를 때마다 노브 사이 RGB LED 3개가 번갈아 켜짐(연결 슬롯 표시로 추정)
  - 노브 사이 충전 LED 2개: 빨강 = 충전 중, 초록 = 완충(충전 IC 또는 칩 충전부가 켜는 것으로 추정, 확인 필요)
  - J4: 사각·원형 패드 2개(부트 핀 추정, 확인 필요)
- 칩: **JieLi(杰理) AC6321A**(BD19 = AC632N 계열, QFN32 4×4). 판단 근거는 [칩 식별](#칩-식별-jieli-32핀)
  - 각인 `BP3D136-21A4`는 다른 표기(웹 검색 일치 자료 없음). 각인 위 π 모양 마크 = JieLi 로고(사용자 확인)
  - QFN32 4 × 4 mm. 칩 왼쪽 위 흰 실크 점 = AC6321A **1번 핀(PB0) 모서리**. 칩 표면 딤플·모서리 표시 없음
  - 크리스털 `24.000` = 24 MHz
  - 칩 특성(AC6321A 데이터시트 핀 표): BLE 전용(오디오 핀 없음), USB 두 쌍(USB0 14·15, USB1 28·29), DC-DC(2 SW), 충전 입력(4 LDOIN). 나머지 사양은 펌웨어 세션 정리 대기
- USB(공장 펌웨어, PM이 읽기만 함, 2026-11-15)
  - **HID 키보드로 잡힘**. 처음 한 번은 안 잡혔음(원인 미확인: 케이블·전원 스위치 추정)
  - VID:PID **`514C:8850`**, bcdDevice `0x0100`, 시리얼 `CD71134331353930`, 제조사·제품 문자열 없음. VID `0x514C`는 웹 검색으로 소유자 못 찾음
  - 인터페이스 0: 벤더 HID(Usage Page `0xFF00`), Report ID 3, 입력·출력 64바이트. 공장 설정 채널([아래](#공장-설정-프로그램프로토콜-884x-계열-추정))
  - 인터페이스 1: 키보드(ID 1, 6키), 마우스(ID 2), 키보드(ID 4, 9키 + LED 5개), Consumer(ID 5, 16비트)
- 개발 보드 UID: 해당 없음

#### 앞선 판단 (AC6956C, 철회)

- 실크 점을 AC6956C 8번과 9번 사이 모서리로 보고, 사용자 계수를 "9 − 계수"로 옮겨 AC6956C 번호로 적었음. 이 공식은 AC6956C를 전제한 것이라 버림
- "AC6321A 제외"도 핀을 AC6956C 번호로 센 결과(VBAT 11, BTAVDD 14, USB 22·23으로 옮겨 비교)라 잘못. 철회
- AC6956C·JL7016C8 구별에서 잰 "31번" = AC6321A 23번 PB8(GPIO). GND와 도통 없음은 그대로 맞음
- 옛 번호(16 안테나, 17·18 크리스털, 23·24 USB, 31 비접지)는 AC6321A 번호(8, 9·10, 14·15, 23)로 바꿈

- 남은 일: 키 행렬·노브·LED 핀을 AC6321A 핀 이름으로 정리(체크리스트 17)
- 이식 메모(미검증): 공식 SDK(fw-AC63_BT_SDK, `cpu/bd19` = AC632N 공식 지원)와 ROM USB 장입(UBOOT), 공개 백업 도구가 있음 → [JieLi SDK·장입](#jieli-sdk장입-조사). 공장 펌웨어는 지워도 됨([공장 펌웨어](#공장-펌웨어-지워도-됨))
- 공통 어려운 점: 키 행렬 스캔(지금 HAL은 키마다 한 핀), 노브 2개(지금 펌웨어는 노브 1개 보드만 확인), 새 칩 HAL·무선 스택, 공장 펌웨어 백업 불가 가능성

#### 장입: USB 다운로드 모드(UBOOT)

- 칩 ROM의 USB 다운로드 모드. 들어가면 PC에 표준 USB 저장장치(SCSI, 이름 "UBOOT", 사용자 명령 `0xFB`·`0xFC`·`0xFD`)로 보임
- **공장 펌웨어에서 PC USB만으로 진입됨**(PM 시험, 사용자 승인 "보내 봐" 뒤, 2026-11-15)
  - 공장 벤더 HID(인터페이스 0)에 `03 EF EF` + 0 채움(65 B 쓰기) → 쓰기 결과 −1, 장치가 끊기고 USB 저장장치로 다시 잡힘
  - 다시 잡힌 장치: `4C4A:3442`, "BD19 UBOOT1.00"(USBSTOR `VEN_BD19` `PROD_UBOOT1.00` `REV_1.00`)
  - `03 FC FC`(기종 설정)는 안 보냄
  - → 처음 설치에 어댑터·동글 필요 없음(사용자: 둘 다 구입 불가, USB 장입만)
- 칩: UBOOT 이름 BD19 = AC6321A(AC632N 계열)와 일치
- **RAM 로더 동작 안 함**(PM 시험 3회, 2026-11-15): jl-uboot-tool 방식으로 SDK `cpu/bd19/tools/bd19loader.bin`을 UBOOT로 RAM 0x2000에 올려 실행
  - 그대로 보냄: 점프 응답 OK 뒤 첫 명령에서 멈추고 리셋
  - MengLi를 한 번 더 걸고 보냄: 점프에서 바로 리셋
  - 동작 확인된 것: `03 EF EF` → UBOOT → RAM 쓰기(`FB06`)·점프(`FB08`)
  - 플래시 ID·용량은 미확인 → 우리 펌웨어를 올린 뒤 SDK로 읽기

| 경우 | 진입 방법 | 근거 |
|---|---|---|
| 처음 설치(공장 펌웨어) | 공장 벤더 HID에 `03 EF EF` → ROM UBOOT | PM 시험(확인, 2026-11-15) |
| 우리 펌웨어 설치 뒤 | 벤더 HID BOOT 명령(CH32V203 `CMD_BOOT` 자리) → SDK `go_mask_usb_updata()`(인터럽트 끄기 → `nvram_set_boot_state(UPGRADE_USB_SOFT_KEY)` → 재시작) → ROM UBOOT. GUI BOOT 버튼으로 가능 | SDK `apps/common/device/usb/device/msd_upgrade.c`(실물 미시험) |
| 앱이 USB 전에 멈춤(복구) | 플래시 부팅 실패면 ROM이 스스로 UBOOT. 부팅은 되나 USB가 안 되면 USB_KEY 신호(하드웨어)만 남음 | jielie·jl-uboot-tool 문서 |

- 그 밖의 진입(참고, 지금은 안 씀)
  - USB_KEY 신호(`0x16EF`): 칩 USB 선(D+·D−)을 GPIO처럼 흔드는 16비트 신호(약 50 kHz, MSB 먼저), PC USB 호스트로는 못 만듦 → JieLi 동글 또는 CH32V203 어댑터(`firmware/jl_usbkey_ch32v203`, **보류**, [README](../../firmware/jl_usbkey_ch32v203/README.md)). 어느 선이 클럭인지 자료끼리 다름
  - UART_KEY(`0x68AF`, 핀은 칩마다 다름, BD19 확인 필요), ISP_KEY(USB 핀): 하드웨어 필요
  - 플래시가 비었거나 부팅에 실패하면 자동 진입. 핀 스트래핑 방식은 아님

#### 백업·쓰기 도구 (jl-uboot-tool)

- `github.com/kagaimiq/jl-uboot-tool`: MIT, Python 스크립트(장치 찾기 jldevfind, RAM 코드 실행 jlrunner, scsiio). 명령 read·write·erase·erasechip(안 될 수 있음)·dump. BR23 "Working", BD19 "unknown"(실물 확인 필요)
- ROM UBOOT1.00은 플래시 읽기에 RAM 로더가 필요할 수 있음(jlrunner가 처리). BD19 로더는 이 칩에서 동작 안 함(PM 시험, [위](#장입-usb-다운로드-모드uboot))
- GUI에 붙이는 방안: (1) 필요한 부분(장치 찾기·칩 정보·플래시 읽기)만 MIT 고지와 함께 `gui/core/`로 옮김(권장, 읽기 먼저) (2) CLI를 하위 프로세스로 실행
- Windows: 표준 저장장치라 기본 드라이버로 붙을 것(추정). SCSI 직접 명령은 **관리자 권한**이 필요할 수 있음(미확인)
- 플래시 용량·ID는 미확인(로더가 안 돼 UBOOT로 못 읽음, 우리 펌웨어를 올린 뒤 SDK로 읽기). 칩 키·암호화 요구 여부 미확인. 공식 장입 도구(`isd_download`·`download.bat`) 결과 이미지를 쓸지 미정

#### GUI 흐름 (설계안, 구현은 GUI 세션)

1. 장입 화면에서 JUZH_3B4 → 진입 방법 고름(USB만, core `ENTRY_METHODS`·`enter_uboot`): 공장 펌웨어 = 벤더 HID(`514C:8850` Report 3)에 `03 EF EF` + 0 채움 65 B, 우리 펌웨어 = BOOT 명령
2. UBOOT 디스크(`4C4A:3442`, 이름 "UBOOT") 기다리기(20초). 못 찾으면 안내(관리자 권한, 포트·허브)
3. RAM 로더 실행(BD19 `bd19loader.bin`, 0x2000) → 칩·플래시 ID·용량 표시. 처음이면 기록, 다음부터 대조(다르면 멈춤). **BD19 로더는 이 칩에서 동작 안 함(PM 시험, [위](#장입-usb-다운로드-모드uboot)) → 3~5단계는 다시 설계 필요(GUI 세션)**
4. **백업(기본 켬, 끌 수 있음)**: 전체 읽기 두 번 비교 → 파일 + SHA-256 저장, 경로 표시
5. 쓰기 확인(이미지 이름·크기, "지우고 씀") → 쓰기 → 확인 읽기
6. 재시작 → 앱 HELLO 기다림 → 완료

- core(Qt 없음, GUI 세션): [gui/core/jluboot.py](../../gui/core/jluboot.py)(UBOOT SCSI 명령, jl-uboot-tool 일부 이식·MIT 고지, Windows SPTI·드라이버 변경 없음, RAM 로더, 칩·플래시 ID 대조, 백업 두 번 읽기 비교·SHA-256, 지우기·쓰기·확인 읽기·재시작), [gui/core/jl_usbkey.py](../../gui/core/jl_usbkey.py)(어댑터, 보류: 화면·보드 목록에서 안 씀). 가짜 장치 시험 `tests/gui/test_jluboot.py`. 화면·보드 목록 등록은 아직

| 단계 | CH32V203(SAYO_3X3 등) | JUZH_3B4(AC6321A) |

### 공장 설정 프로그램·프로토콜 (884x 계열 추정)

- 제조사 설정 프로그램: `szxiaozi.com/tool.zip`(사용자가 받음, 저장소 밖에 보관)
  - 안의 파일: Windows `MINI_KEYBOARD.exe`(Qt5, hidapi), Mac `MINI_KEYBOARD.pkg`
  - 실행하지 않고 문자열만 봄(PM, 2026-11-15): `hid_write`/`hid_read` 사용. 레이어·LED 모드·RGB LED·멀티미디어·마우스 키 설정 화면. 칩 이름 문자열 없음
- 공개 도구 `ch57x-keyboard-tool`(`github.com/kriomant/ch57x-keyboard-tool`, 소스 1.6.2)과 대조
  - 같은 계열 저가 매크로 키보드용. README 지원 목록에 "3×4 with 2 knobs (Bluetooth version)"이 있음
  - 기본 VID `1189`(Trisat), PID `8840`·`8842`·`8890`. 소스는 PID `0x8850`도 884x 방식으로 처리(자동 검색 목록에는 없음, `--product-id`로 지정)
  - 설정 패킷: 64바이트, 첫 바이트 `0x03`(예: `03 FE` 키 레이어+1 …) → 이 보드 벤더 HID의 Report ID 3·64바이트와 맞음
- 결론(추정): 공장 펌웨어는 이 "884x" 설정 프로토콜 계열. VID만 `514C`로 다름. 도구 이름의 ch57x는 계열 이름일 뿐 칩과 무관(칩은 JieLi)
- 뜻: **공장 펌웨어를 그대로 두고 키 설정만 바꾸는 길**이 있을 수 있음(장입 불필요)
  - 단 벤더 채널에 쓰면 공장 설정 영역이 바뀜 → **사용자 승인 뒤에만**. 지금까지 설정을 바꾸는 명령은 보내지 않음

#### 공장 채널 읽기 시험 (2026-11-15)

- 사용자 지시로 PM이 시험. 설정을 바꾸는 명령은 보내지 않음
- 수동 대기 3초: 장치가 먼저 보내는 보고서 없음
- Report ID 3 + 0으로 채운 64바이트(공개 도구의 초기화 패킷과 같은 내용): 응답 없음
- 조회 명령 `03 FB FB FB` + 0(65바이트 쓰기, 64바이트 읽기): 공장 프로그램을 역어셈블해서 찾음(실행 안 함). 공장 프로그램이 연결할 때 보냄
- 응답: `03 FB 0C 02 0B` + 0
  - 공장 프로그램은 응답 [2]·[3]·[4] 세 바이트를 전역 변수 3개에 저장. 문자열 `Cur_KeyBoard_KeyNum[2]`가 있음
  - 해석(추정): 키 12개(`0x0C`), 노브 2개(`0x02`), 기종·버전 `0x0B`
- 쓰기 명령(예: `03 FE …`)은 미시험. 사용자 승인 뒤

#### 쓰기 명령 (조사 중, 2026-11-15)

- 장치에는 아무것도 보내지 않음. 문서·역어셈블 분석만
- 공개 도구 884x 형식(출처: `ch57x-keyboard-tool` 1.6.2 `k884x.rs`)
  - 키 지정: `03 FE 키ID 레이어+1 종류 00 00 00 00 00` + 데이터. 종류: 1 키보드, 2 미디어, 3 마우스
    - 키보드: [10] = 개수, 이어서 (수정키, 키코드) 쌍. 최대 18쌍
    - 미디어: [10] = 0, [11..12] = Consumer 코드(리틀 엔디언)
  - 매 지정 뒤 `03 AA AA`, `03 FD FE FF`, `03 AA AA`
  - 키ID: 키 1~12 = `0x01`~`0x0C`. 노브 0 = `0x10`/`0x11`/`0x12`(반시계/누름/시계), 노브 1 = `0x13`/`0x14`/`0x15`. 레이어 0~2
  - LED: `03 FE B0 레이어+1 08 00 05 01 00 코드 00 34`, 끝 `03 FD FE FF 00 3D`
- 공장 프로그램 역어셈블(실행 안 함)에서 찾은 명령

| 명령 | 쓰임 | 상태 |
|---|---|---|
| `03 FB FB FB` | 조회(키 수·노브 수·기종) | 시험 완료 |
| `03 FA …` | 쓰기 뒤 64 B를 읽는 반복문에서 씀. LED 패킷도 `03 FA B0 레이어`로 만듦 | 미시험. 기종 바이트(조회 응답 [4])를 9와 비교하는 분기 있음 |
| `03 FE …` | 키 패킷 표에 있음 | 어느 기종용인지 미확인 |
| `03 EF EF` | 인자 없음 | **UBOOT 진입(확인)**: 보내면 끊기고 `4C4A:3442` "BD19 UBOOT1.00"으로 다시 잡힘(PM 시험, 2026-11-15) |
| `03 FC FC kk nn vv` | 기종 설정: 키 수 kk, 노브 수 nn, 변형 vv | 뜻 확인(정적 분석, PM, 2026-11-15). 장치에 안 보냄. 아래 표 |

- `03 FC FC` 기종 설정(공장 프로그램 `MINI_KEYBOARD.exe` 정적 분석, PM, 2026-11-15. 장치에 보내지 않음)
  - 숨은 슬롯 `Set_Keyboard_Ver_SLOT(int)`, 버튼 이름 "3+1KEY" … "15+3KEY", "4+1_2KEY", 쓰기 뒤 로그 "Witer OKOK Key Num"
  - 조회 응답 `03 FB 0C 02 0B`의 `0C 02`(12키·노브 2)와 같은 형식 → 공장 펌웨어는 여러 기종 공용이고, 저장한 기종 값으로 동작(추정)
  - 우리 펌웨어에는 필요 없음(기록만)

## 4. LED

- 키 LED: 종류(단색/RGB/WS2812류)·구동 방식 확인 필요
- 노브 사이 RGB LED 3개: 버튼으로 번갈아 켜짐(슬롯 표시 추정). RGB 4다리 또는 WS2812류, 확인 필요

## 5. 부팅·장입

- 장입 경로(조사, 미검증): 칩 ROM의 USB 다운로드 모드(UBOOT, PC에는 USB 저장장치). 핀 스트래핑 아님([JieLi SDK·장입](#jieli-sdk장입-조사))
  - 우리 펌웨어 설치 뒤: GUI BOOT 명령 → SDK `go_mask_usb_updata()` → UBOOT(소프트웨어만으로)
  - 처음 설치: 공장 벤더 HID에 `03 EF EF` → UBOOT `4C4A:3442` "BD19 UBOOT1.00"(확인, 2026-11-15). 플래시가 비었거나 부팅 실패면 자동 진입
  - GUI core(`gui/core/`의 `jluboot.py`): 진입 방법 공장 = `03 EF EF`, 우리 = BOOT 명령(`ENTRY_METHODS`·`enter_uboot`). UBOOT 장치 `4C4A:3442`, BD19 RAM 로더 0x2000(이 칩에서 동작 안 함, PM 시험)
  - USB_KEY 어댑터(`jl_usbkey_ch32v203`)는 보류([README](../../firmware/jl_usbkey_ch32v203/README.md))
  - 자체 부트로더는 따로 없음(ROM UBOOT가 그 역할). 단계별 대응은 [장입 방향](#장입-방향-사용자-결정-2026-11-15)
- 칩 키·암호화 요구 여부는 미확인
- 벤더 HID 채널(인터페이스 0)은 공장 설정용, 884x 계열 프로토콜로 추정. 조회 `03 FB`, UBOOT 진입 `03 EF EF` 시험함. 설정 쓰기는 안 함
- 장입 없이 공장 펌웨어의 키 설정만 바꾸는 길이 있을 수 있음([1절](#공장-설정-프로그램프로토콜-884x-계열-추정)). 사용자 승인 뒤에만
- J4 용도 확인 필요(UBOOT 진입이 핀 스트래핑이 아니라는 자료가 있어 부트 핀 추정은 약해짐, 추정). 연결 금지, 연결처만 잼
- 장입은 사용자가 "ㄱㄱ"라고 한 뒤에만. 공장 펌웨어는 지워도 됨([1절 공장 펌웨어](#공장-펌웨어-지워도-됨)). 장입 방향은 우리 절차와 같은 모양([장입 방향](#장입-방향-사용자-결정-2026-11-15))
