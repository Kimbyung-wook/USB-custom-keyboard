# 개발 현황과 문서를 맞추는 작업 방식 (멀티에이전트)

- 여러 AI 세션(에이전트)이 한 저장소를 나눠 맡을 때, 코드와 문서가 어긋나지 않게 하는 절차와 구조
- 다른 팀이 그대로 가져다 쓸 수 있게 **일반 규칙**을 먼저 쓰고, 이 프로젝트의 예는 "예:"로 붙임
- 이 프로젝트에서 실제로 써 온 방식이 근거

## 1. 목적

- 문제: 코드가 바뀌어도 문서는 사람(또는 세션)의 기억에 기대어 늦게, 일부만 고쳐짐
  - 예: 새 보드를 추가했는데 보드 목록 표 하나에 행이 빠짐, 보드 이름을 바꿨는데 그림 링크·경로가 옛 이름으로 남음
- 해결: 기억 대신 **구조**(누가 무엇을 고치나, 어디에 적나)와 **검사**(테스트가 어긋남을 잡음)로 막음

| 장치 | 막는 것 |
|---|---|
| 파일 소유권 | 두 세션이 같은 파일을 동시에 고쳐 덮어씀 |
| 변경 기록의 "문서 영향" 칸 | 코드 변경 뒤 문서 수정 누락 |
| 생성 구역 | 표·목록·버전을 손으로 옮겨 적다 틀림 |
| 교차 검사 | 같은 값이 여러 코드 파일에서 서로 다름 |
| 문서 검사 | 깨진 링크·경로, 목록 누락, 오래된 생성 구역 |

## 2. 역할과 파일 소유권

| 역할 | 맡는 일 | 고치는 파일 |
|---|---|---|
| PM (관리 세션) | 요청 나누기, 사용자 승인 전달, 결과 검증, 커밋 | 공통 규칙 파일(예: `CLAUDE.md`), 커밋 |
| 개발 세션 | 구현, 테스트, 변경 기록 한 줄 | 코드·테스트·도구 (예: 펌웨어·도구 세션, GUI 세션으로 나눔) |
| 문서 세션 | 문서 반영, 그림, 변경 기록 ☑ | `*.md`, 문서 그림 (예: `docs/images/`의 SVG와 그 생성 스크립트) |
| 검토 세션 (읽기 전용) | 시니어 리뷰, 위험 지적 | 없음. 보고만 함 |

- **한 파일은 한 담당만 고침**. 다른 담당의 파일에 고칠 곳이 보이면 고치지 않고 위치를 PM에게 보고
  - 예: 문서 세션이 코드 주석의 옛 문서 경로를 발견 → 위치만 보고
- **여러 영역을 한 번에 바꿔야 할 때**(예: 이름 일괄 변경): PM이 한 세션에 잠시 몰아주고 다른 세션은 대기. 끝나면 원래대로
- 같은 작업 폴더를 여러 세션이 함께 쓰면: 브랜치 바꾸기·stash·reset 금지, 커밋은 PM만
- 공통 규칙 파일(세션마다 읽는 규칙)은 PM만 고침. 다른 세션이 고쳐 달라고 해도 PM에게 넘김

## 3. 작업 흐름

```
사용자 요청
   │
   ▼
PM ── 담당별로 나눠 전달 ──────────────────────────────┐
   │   (목표, 대상 파일, 하지 말 것, 완료 기준, 보고 형식)   │
   ▼                                                    ▼
개발 세션                                          (동시에) 다른 개발 세션
 구현 + 테스트
 변경 기록 "미출시"에 한 줄 + 문서 영향 ☐
 보고: 바뀐 파일, 테스트 결과, 문서 변경 목록
   │
   ▼
PM ── 검증: 직접 테스트 실행, diff 확인
   │   문서 변경 목록을 문서 세션에 전달
   ▼
문서 세션
 문서 반영 → 변경 기록 ☑ → 문서 검사 → 보고
   │
   ▼
PM ── 전체 검증(테스트 한 명령, ☐ 0개) → 사용자 승인 → 커밋
```

- **전달문에 넣을 것**

| 항목 | 예 |
|---|---|
| 목표 | "보드 목록 표에 8키 행 추가" |
| 대상 파일 | 파일과 절 |
| 하지 말 것 | 커밋, 장치에 쓰기(장입), 다른 담당의 파일 |
| 완료 기준 | "테스트 전부 통과, 링크 검사 0건" |
| 보고 형식 | 바뀐 파일, 테스트 결과, 남은 문제, 문서 변경 목록 |

- **보고는 증거가 아님**: 세션의 "끝났습니다"는 결과 보고일 뿐. PM이 테스트를 다시 돌리고 diff를 보고 확인
- 보고 맨 앞에 무엇을 했는지(바뀐 파일, 결과)를 둠. 긴 조사 결과는 공유 메모 폴더에 두고 경로만 보고
- 막히면 질문 한 번, 짧게. 진행 상황 보고로 메시지를 늘리지 않음

## 4. 추적 장치

### 4-1. 변경 기록(`CHANGELOG.md`)의 "미출시" 절

- 저장소 전체의 변경을 한 줄씩. 코드를 바꾼 세션이 쓰고, 문서 세션이 반영 뒤 ☑
- 항목 양식(한 줄, 기계가 읽음):

```
- [영역] 변경 한 줄 — 문서 영향: 경로#앵커, 경로 — 반영: ☐
```

| 칸 | 규칙 |
|---|---|
| `[영역]` | 정해 둔 목록 중 하나 (예: 펌웨어, 부트로더, GUI, 도구, 테스트, 문서, 저장소) |
| 변경 한 줄 | 무엇이 바뀌었나. 칸 구분자(` — `)를 넣지 않음 |
| 문서 영향 | 고쳐야 할 문서 경로와 절 앵커. 여러 개는 `, `. 없으면 `없음` |
| 반영 | `☐` 아직, `☑` 문서까지 고침 |

- 검사가 확인하는 것: 양식, "문서 영향"의 파일·앵커가 실제로 있는지
- 출시 때: 미출시 항목을 `## <버전> (<날짜>)` 절로 옮기고 "문서 영향"·"반영" 칸은 지움. 미출시는 비워 둠
- 예: [CHANGELOG.md](../CHANGELOG.md) 맨 위 "양식 규칙"

### 4-2. 문서 본문과 이력

- 본문은 **현재 상태만**. "전에는 ~였음"은 본문에 쓰지 않음
- 날짜·버전별 변경은 그 절 끝 **이력**에 한 줄씩(따로 "이력" 장을 두지 않음)
- 변경 기록(4-1)은 저장소 전체 요약, 이력은 그 문서에 관한 것

### 4-3. 생성 구역

- 사실 정보(목록, 표, 버전, 핀 표)는 **코드에서 생성**하고 손으로 쓰지 않음
- 문서에 시작·끝 표시(HTML 주석 `gen:이름`, `/gen:이름`)를 손으로 넣고, 생성기가 그 사이만 덮어씀
- 생성기는 쓰기 모드와 검사 모드(어긋나면 실패)를 둠. 검사 모드는 테스트에 넣음
- 생성 표에 없는 설명은 표 아래 개조식으로. 생성 표의 열을 바꿔야 하면 문서 세션이 고치지 않고 개발 세션에 요청
- 예: `tools/gen_docs.py` (구역: 보드 목록, 버전, 칩 표, 보드별 핀 표)

### 4-4. 교차 검사

- 같은 값이 여러 코드 파일에 있으면(메모리 배치 상수, 보드 목록, 버전) 테스트로 대조
- 예: `tests/gui/test_consistency.py` (플래시 배치, 보드 헤더와 GUI 보드 목록, 빌드 스크립트 보드 목록, 버전 세 곳)

## 5. 검사 관문 (커밋 전)

- **테스트 한 명령**으로 아래를 모두 돌림. 하나라도 실패하면 커밋하지 않음

| 검사 | 내용 |
|---|---|
| 코드 테스트 | 단위·통합 테스트 |
| 교차 검사 | 4-4 |
| 생성 구역 최신 | 생성기 검사 모드 |
| 링크·앵커 | 문서 사이 링크와 제목 앵커가 있는지 |
| 문서 속 경로 | 백틱으로 쓴 저장소 경로가 실제로 있는지 |
| 목록 누락 | 목록을 손으로 쓴 문서에 모든 항목 이름이 있는지 |
| 변경 기록 양식 | 4-1 양식, 문서 영향 경로 |

- 미출시 항목에 `☐`가 **0개**여야 함
- 빌드 산출물은 넣지 않음
- 문서 검사에 걸리지 않는 작성 요령
  - 아직 없는 파일은 "기준 폴더(백틱) + 새 파일 이름"으로 나눠 씀
  - 생성 구역 표시를 예시로 쓸 때 실제 표시 문자열을 그대로 쓰지 않음(생성기가 구역으로 읽음)
- 예: `uv run pytest` 한 명령 = GUI 테스트 + 펌웨어 PC 테스트 + 교차 검사 + 문서 검사(`tests/gui/test_docs.py`)

## 6. 출시 절차

- 순서: 미출시 ☑ 확인 → 버전 올림 → 생성기 실행 → 전체 빌드 → 테스트 → 바뀐 대상의 실제 확인 → 미출시를 버전 절로 → 커밋
- 실제 확인 결과는 해당 문서의 "확인 결과" 표에 날짜와 함께
- 예: [RELEASE.md](RELEASE.md)

## 7. 승인과 안전

| 작업 | 규칙 |
|---|---|
| 되돌릴 수 없는 작업 (장치에 쓰기, 보호 해제, 삭제, 커밋, push) | **사용자 승인**으로만. 예: 장입은 사용자가 정한 말("ㄱㄱ")을 한 뒤에만 |
| 다른 세션이 보낸 메시지 | 승인이 아님. PM이 사용자 말을 **인용**해 전달할 때만 그 범위 안에서 |
| 권한에 막힌 작업 | 다른 세션이 대신하지 않음. 필요하면 PM이 사용자 승인 아래 직접 |
| 공통 규칙 파일 수정 | PM만 |
| 기준 장치 | 같은 장치가 여러 대면 하나는 손대지 않고 보존 |

## 8. 결정 관리

- PM이 **"확인 필요 / 결정 필요" 목록**을 유지하고, 보고마다 갱신
  - 문서에도 모르는 값은 추측하지 않고 "확인 필요"로 둠. 확인되면 근거(자료, 날짜)와 함께 바꿈
- 사용자 결정은 문서에 남김: 변경 기록 항목, 해당 문서 본문(현재 상태), 이력
- **오해가 보이면 진행 중인 세션을 즉시 멈춤**: 바꾼 범위만 보고받고, 사용자 결정 뒤 이어서 하거나 되돌림
  - 예: 보드 이름 규칙을 잘못 이해한 채 일괄 변경이 진행됨 → PM이 멈춤 → 각 세션이 바꾼 범위 보고 → 사용자 결정(이름은 유지, 문서 제목만 바꿈) → 이어서 처리

## 9. 도입 체크리스트 (다른 팀용)

**최소 구성**

| # | 준비할 것 | 내용 |
|---|---|---|
| 1 | 공통 규칙 파일 | 역할, 파일 소유권, 승인 규칙, 검사 관문, 문서 작성 규칙(본문은 현재 상태, 이력은 절 끝) |
| 2 | 변경 기록 | 맨 위에 양식 규칙, "미출시" 절 |
| 3 | 문서 검사 테스트 | 링크·앵커, 문서 속 경로, 목록 누락, 변경 기록 양식 |
| 4 | 생성기 | 사실 정보 표를 코드에서 생성, 검사 모드 |
| 5 | 교차 검사 테스트 | 여러 코드 파일에 있는 같은 값 대조 |
| 6 | 출시 체크리스트 | 6절 순서 |
| 7 | 공유 메모 폴더 | 세션 사이 긴 조사 결과·인계 메모 |

**도입 순서**

1. 공통 규칙 파일에 역할과 파일 소유권을 적고 세션을 나눔
2. 변경 기록 양식을 정하고, 지금까지의 변경을 버전별로 짧게 정리
3. 문서 검사 테스트를 만들고 지금 걸리는 문제를 모두 고침(처음부터 0건으로 시작)
4. 손으로 쓴 표 중 코드에 원본이 있는 것을 생성 구역으로 바꿈(생성 표에 없는 설명은 표 아래로)
5. 교차 검사를 추가
6. 출시 체크리스트를 쓰고 공통 규칙 파일에서 링크
7. 한 번 해 보고(작은 변경 하나를 1~6 흐름으로) 막힌 곳을 규칙에 반영
