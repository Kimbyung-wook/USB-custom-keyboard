# CH32V203 자체 부트로더

> 문서 성격: **설계** + 개발자용 절차. 사용자 절차(설치·업데이트·복구)는 [MANUAL 8장](MANUAL.md#8-펌웨어-업데이트), 보드별 진입 키는 [BOARDS.md](BOARDS.md)

- 목적: BOOT 브리지 없이 펌웨어 업데이트. **왼쪽 아래 키(9키: 키 7, 8키: 키 5, 12키: 키 7)를 누른 채 꽂으면** 부트로더, 또는 GUI [업데이트 모드로 전환]
- 배경: WCH ROM 부트로더는 소프트웨어로 들어가도 앱으로 돌려보냄 ([시험](../tests/hw/ch32v203/test_ch32v203/README.md) "실험: 소프트웨어로 부트로더 진입")
- 대상: SAYO_3X3(진입 키 7), SAYO_2X4(진입 키 5), SAYO_2X6(진입 키 7, PA7). 진입 키·LED 핀은 보드 파일에서 읽음(`BOARD_BOOT_KEY`, `BOARD_KEY_PINS`, `BOARD_LED_PINS`, `BOARD_KEY_LED_PINS`)
- 상태: 구현·빌드 완료(부트로더 4.4 KB), PC 쪽 pytest 통과. 하드웨어 확인: 설치, 앱 시작, 키 7 진입·HELLO, HID 앱 장입(키 7, BOOT 명령 모두), 장입 뒤 설정 유지, GUI 업데이트 창, 장입 중 뽑기 → 다시 장입. 8키(SAYO_2X4): 설치, 키 5 진입, HID 장입 확인. 12키(SAYO_2X6): 설치, 키 7 진입·보라 LED, HID 장입 확인
  - 9키 장치는 1.7.0 `-Full`로 부트로더를 새 빌드로 바꿈. 8키 장치는 이전 빌드 그대로(옛 이름 `2X4V_RGB`를 알림, `boards.py` 별칭으로 장입에 문제없음)

## 결정

- 진입 키: 키 7(PB2). PB2는 BOOT1 핀이지만 BOOT0이 0이면 영향 없음
- WRP 쓰기 보호: 안 씀 (부트로더의 주소 검사로 충분, 되돌리기 쉬움)
- LED: 전체 **보라** (CH552 보드의 업데이트 모드 색과 같음). 보드 파일에 LED 핀(`BOARD_LED_PINS`, `BOARD_KEY_LED_PINS`)이 없으면 LED를 구동하지 않고 빌드됨

## 플래시 배치 (64 KB, `src/hal/ch32v203/boot_layout.h`)

| 주소 | 크기 | 내용 |
|---|---|---|
| 0x08000000 ~ 0x08001FFF | 8 KB | 부트로더 |
| 0x08002000 ~ 0x0800EEFF | 52992 B | 앱 (본 펌웨어, 지금 약 12 KB) |
| 0x0800EF00 ~ 0x0800EFFF | 256 B | 앱 정보: 매직 `APP1`, 길이, CRC32(zlib), 검사값 |
| 0x0800F000 ~ 0x0800FFFF | 4 KB | 설정 저장 (업데이트해도 유지) |

- RAM 끝 16바이트(0x20004FF0~): 부트로더·앱 공용 표시. 두 링커 모두 RAM 길이 0x4FF0
- 지워진 플래시는 0xFF가 아니라 `0xE339E339`로 읽힘 → 앱 정보는 매직·검사값으로 판단

## 시작 순서

1. 다음 중 하나면 **부트로더에 머묾**
   - RAM 표시 `0xB0075EED`: 앱의 BOOT 명령(0x06)이 남김. 읽고 바로 지움
   - 키 7 눌림: 풀업 후 1 ms 기다려, 1 ms 간격 20번 모두 눌림
   - 앱 정보가 없거나 틀림(매직, 검사값, 길이, CRC). 장입이 끊긴 경우 포함
2. 아니면 GPIOA/B·AFIO 리셋, SysTick 정지, 인터럽트 끔 → 0x00002000으로 점프
- 머신 모드로 실행(시작 코드를 sed로 수정) → 앱 시작 코드가 머신 CSR을 쓸 수 있음

## USB·명령

- USBFS, 인터럽트 없이 폴링. **Vendor HID 하나만**(드라이버 설치 불필요)
- VID:PID `1209:C55E` (앱은 `1209:C55D`), 제품 문자열 `MacroKeyboard Bootloader`
- 64바이트 리포트. 머리말 `cmd, seq, status`, 응답은 `cmd | 0x80`

| 코드 | 이름 | 요청 | 응답 |
|---|---|---|---|
| `0x01` | HELLO | - | [3..4] 버전 1.0, [5..20] 보드 이름, [21..32] 칩 UID, [33] 앱 주소, [37] 앱 최대, [41] 페이지 256, [43] 앱 유효, [44] WRITE 최대 56 |
| `0x10` | ERASE | - | 앱 정보 페이지 먼저 지움 → 앱 영역(4 KB 단위) 지움 |
| `0x11` | WRITE | [2] 주소 u32, [6] 길이(최대 56), [8..] 데이터 | 페이지(256 B)를 넘지 않아야 함. RAM에 모아 페이지 단위로 쓰고 비교 |
| `0x12` | CHECK | [2] 길이, [6] CRC32 | 남은 페이지를 쓰고 CRC 계산, 맞으면 앱 정보 기록. [3] 계산한 CRC |
| `0x13` | RUN | - | 응답 후 USB 끊고 재시작 → 앱 |

- 상태: 0 OK, 1 모르는 명령, 2 인수 오류, 3 CRC 불일치, 5 플래시 오류
- ERASE 전 WRITE, 앱 영역 밖 쓰기는 거부(부트로더·설정 영역 보호)
- 앱 정보는 CHECK가 성공해야만 기록 → 끊기면 다음에 꽂아도 키 없이 부트로더
- 쓰는 동안 LED 보라 깜빡임

## 앱(본 펌웨어) 변경

- `Makefile.ch32v203`의 `BOOTLOADER ?= 1`: FLASH 시작 0x00002000, 상한 52992 B. `BOOTLOADER=0`이면 부트로더 없는 배치(앱 0x08000000, 바꿀 때 `rm -rf build`)
- BOOT 명령(0x06): 300 ms 뒤 USB 끊고 200 ms 기다린 다음 RAM 표시 쓰고 재시작 (`hal_enter_bootloader`)
- `make flash`(wchisp로 앱만)는 `BOOTLOADER=1`에서 거부 → 전체 이미지 사용

## 빌드

- `tools\build_fw.ps1 -Board sayo_3x3`(8키는 `sayo_2x4`, 아래 파일 이름도 보드 이름만 다름): 앱 + 부트로더 + 전체 이미지
  - 앱: `firmware/macro_keyboard/build/ch32v203/macro_keyboard-SAYO_3X3.bin`
  - 전체: `firmware/bootloader_ch32v203/build/full-SAYO_3X3.bin` (부트로더 + 앱 + 앱 정보, 61200 B, `mkfull.py`)
- 부트로더만: `firmware/bootloader_ch32v203`에서 `mingw32-make` (8 KB 넘으면 실패)
- 헤더 의존성(`-MMD -MP`): `boot_layout.h`·보드 파일만 고쳐도 다시 빌드. `make full`은 `EXTRA_DEFS`(빌드 날짜)를 앱 빌드에 넘김

## 설치·업데이트

- 아래는 9키 예(8키는 `-Board sayo_2x4`, 키 5). 단계별 사용자 절차는 [MANUAL 8장](MANUAL.md#처음-설치-공장-펌웨어)
- 처음 한 번(공장 펌웨어 또는 부트로더 없음), 부트로더 교체: `tools\flash.ps1 -Board sayo_3x3 -Full`
  1. BOOT 브리지 이은 채 꽂기 → `wchisp info`로 칩 CH32V203C8U6, 보드 UID, 보호 없음 확인 → `yes`
  2. wchisp가 `bootloader-<BOARD>.bin`(8 KB 이하)만 씀. wchisp는 최소 8섹터(0x0000~0x1FFF)를 지움. 부트로더 8 KB 영역 안이라 앱·설정은 그대로
  3. 브리지 떼고 진입 키를 누른 채 다시 꽂기 → `hidboot`이 앱(`-Bin`)을 씀
  - 설정: 우리 펌웨어가 있던 칩은 남음. 공장 펌웨어(읽기 보호)는 보호를 풀 때 전부 지워짐
  - 매개변수: `-Bootloader`(부트로더 이미지, 기본 `bootloader-<BOARD>.bin`), `-Bin`(앱, 두 경우 모두)
  - `full-<BOARD>.bin`(부트로더 + 앱 + 앱 정보)은 빌드가 계속 만들지만 `flash.ps1`은 안 씀
  - 자체 부트로더로 하는 업데이트는 앱 영역만 지움 → 설정 유지
  - 9키 실측(2026-11-07): 부트로더 교체 → 키 7로 앱 1.7.0 장입 → `check_device` v1.7.0, 설정(슬롯 9개) 유지
- 이후: 브리지 불필요
  - GUI 업데이트 창: [업데이트 모드로 전환] 또는 키 7 누른 채 꽂기 → 칩 표에 "자체 1.0" → [장입]
  - 스크립트: `tools\flash.ps1 -Board sayo_3x3` (키 7) 또는 `-Enter`(잠금 풀린 앱에 BOOT)
  - CLI: `uv run python -m gui.core.hidboot info | flash <bin> [--force] | run [--enter]`
- 부트로더 버전: GUI와 `hidboot`은 부트로더 **1.x**만 받음(HELLO [3] 주 버전). `--force`로도 넘어가지 않음(`--force`는 보드 검사만 건너뜀)
- HID 한 번 쓰기(WRITE) 최대 **56 B** (64바이트 리포트 - 머리 8바이트)
- 옛 이름 장치(보드 확인): 펌웨어 1.7.0·부트로더 1.0은 옛 이름(`3X3V_RGB`, `2X4V_RGB`)을 알림 → `gui/core/boards.py` 별칭으로 같은 보드로 인식. GUI 업데이트 창·`hidboot` 보드 검사는 BOOT 브리지나 `--force` 없이 통과, `check_device`는 "옛 보드 이름" 안내
- 새 펌웨어를 올리면 USB 시리얼(보드 이름)이 바뀌어 Windows가 새 장치로 한 번 잡음. 설정은 남음
- 보드 확인: HID 장입은 `.bin` 식별 문자열(`MKFW1:<보드>:...`)의 보드가 부트로더 HELLO의 보드와 같아야 함. 다르거나 식별 문자열이 없으면 지우기 전에 거부. 시험 펌웨어·다른 보드용은 `--force`(`tools\flash.ps1 -Force`)로만
- 복구: 부트로더가 망가져도 BOOT 브리지 + `-Full`은 언제나 가능

| 위험 | 대책 |
|---|---|
| 업데이트 중 USB 끊김 | 앱 정보를 마지막에 씀 → 부트로더에 머묾, 다시 장입 |

### 시험 중 고친 문제 (2026-11-07)

- 증상: 키 7 보라 LED는 켜지는데 Windows "장치 설명자 요청 실패"
- 진단: `mingw32-make DIAG=1` 빌드는 키 1 LED 색으로 USB 단계를 보여 줌 (빨강 리셋 없음, 파랑 리셋만, 초록 전송, 노랑 SETUP, 청록 주소, 보라 구성). 0.5초 켜짐/꺼짐 = 클럭 정상
- 결과: 파랑(리셋만), 깜빡임 1초 → 클럭·LED 전류는 원인 아님
- 원인: SETUP을 토큰 + 끝점 번호 0으로 판단 → SETUP 때 INT_ST 끝점 칸이 0이 아니면 무시됨
- 수정: SDK처럼 토큰만으로 SETUP 판단 (`usb_hid.c`) → 보라, HELLO 응답
- BOOT 명령 뒤 PC가 부트로더를 못 찾음: 앱이 USB를 끊지 않고 바로 리셋 → PC가 장치가 빠진 줄 모름. 수정: 앱이 USB를 끊고 200 ms 뒤 리셋(`hal_enter_bootloader`), 부트로더 RUN도 200 ms (부트로더 쪽은 다음 `-Full` 장입 때 반영)
- HELLO의 UID 12바이트 중 뒤 4바이트는 `39-E3-39-E3`(칩 UID는 8바이트로 보임). GUI는 앞부분만 비교하므로 문제 없음
